# Phase 9 notes: decisions and results

Companion to `Phases/phase_9.md`. Documents the choices the doc left open and
the actual numbers produced by `train_models_phase9.py` on 2026-08-10.
Implementation: `model_utils.py` (new shared module, functions moved
unchanged from `train_models_phase6.py`), `feature_engineering.py`
(Open/Close targets, Step 2), `merge_and_split.py` (target/horizon column
renames, Step 3), `train_models_phase9.py` (training/evaluation/GPU/loss
logging/spread accuracy, Step 4), `manage_model_storage.py` (Open/Close
serving-combo cleanup, Step 5). `app.py` and `train_models_phase7.py` are
untouched this phase, per the doc's own scope note - see "A known
consequence" below.

## Addendum: `Accuracy_%` removed after review

Added post-training, at the user's request. `Accuracy_%` (100 - MAPE) was
part of Phase 6/7's metric set and got carried into `evaluate_predictions`/
`evaluate_per_stock` in `model_utils.py` unchanged. On review it's the wrong
headline number for this project: it reads as "how good is this model" but
stays flatteringly high (76-99%, see the results below) even for the 48/50
combinations that lose to the naive baseline, since stock prices don't move
much day to day in percentage terms regardless of whether the model is any
good. Removed from both `evaluate_predictions` and `evaluate_per_stock` in
`model_utils.py`; `train_models_phase9.py`'s per-stock sort key switched
from `Accuracy_%` (descending) to `Improvement_over_Naive_%` (descending),
since that's the metric that actually reflects whether a model beats doing
nothing. No retrain needed - the underlying predictions/models don't
change, so `data/phase9_model_comparison_overall.csv` and `_per_stock.csv`
were regenerated by dropping the column and re-sorting the already-computed
rows, not by rerunning `train_models_phase9.py`. `Directional_Accuracy_%` is
a different, legitimate metric and was kept.

## Decision 1: environment split - torch (CUDA) lived in `.venv`, everything else in the global interpreter

Before any code changes, `python -c "import torch"` failed globally, but
`.venv`'s python had `torch==2.13.0+cu130` with `cuda available: True` and
nothing else installed; the global interpreter had
pandas/scikit-learn/xgboost/tensorflow/shap/streamlit but no torch. Installed
the rest of `requirements.txt` into `.venv` (same Python 3.13.14 as global)
rather than the other way around, since `.venv` was the one environment that
already had a CUDA build of torch resolved - reinstalling torch-with-CUDA
globally would have been the more fragile path. `tensorboard` was also
missing from `requirements.txt` despite `torch.utils.tensorboard` needing
it; added as an explicit dependency after the first run crashed on
`ModuleNotFoundError: No module named 'tensorboard'`.

## Decision 2: GPU is actually used by 2 of 5 model types, not all - expected, not a bug

- **GRU (PyTorch)**: real. Confirmed via `nvidia-smi` showing ~741MB
  reserved by the training process while it ran, not just the startup print.
- **XGBoost**: real. Confirmed by XGBoost's own log line (`XGBoost is
  running on: cuda:0`) - the accompanying "mismatched devices" warning is
  about predict-time input living in a CPU DataFrame, not about training.
- **LSTM (TensorFlow/Keras)**: CPU only. `tf.config.list_physical_devices("GPU")`
  returns `[]` - TensorFlow dropped native-Windows GPU support at 2.11+
  (WSL2 or the DirectML plugin would be needed for GPU LSTM on this
  machine). This is exactly the "silent CPU fallback is easy to miss"
  scenario `phase_9.md`'s startup print exists to catch, and it did its job:
  `TensorFlow sees 0 GPU(s): []` showed up immediately in the log instead of
  a slow CPU run silently masquerading as a GPU one.
- **Random Forest / Linear Regression**: CPU only, by design - no GPU path
  in scikit-learn.

## Decision 3: `spread_accuracy` integration - per-ticker CSV, paired by construction rather than by lookup

`phase_9.md` gives the `spread_accuracy(pred_open, pred_close, actual_open,
actual_close)` function itself but doesn't specify how it plugs into the
training loop or where its output goes. Implemented as: train both targets
for a horizon first, stash each model type's predictions/tickers/actuals,
then pair Open/Close predictions by array position once both targets are
done. This works without an explicit ticker-by-ticker lookup because tabular
models (LR/RF/XGBoost) score `test_h` in the same row order for both
targets, and sequence models (LSTM/GRU) build sequences from the same
`test_h_scaled_df` with the same window size for both targets - so
`tickers_seq` comes out in the same order both times. Verified this holds
(`np.array_equal` check before pairing) rather than assumed, as a guard
against silent misalignment. Saved to `data/phase9_spread_accuracy.csv`, one
row per (Ticker, Model, Horizon) - a filename/shape decision, since the doc
named the function but not its output.

## Result: the naive baseline (today's Close) is very hard to beat - the headline finding of this phase

Only 2 of 50 (Model, Target, Horizon) combinations beat the naive baseline
at all, both Linear Regression at 60 days (+1.60% Close, +3.39% Open). Every
other combination - all horizons including 1-day, both targets, all 5 model
types - is negative, i.e. worse than just repeating today's Close.

| Horizon | Best Improvement_over_Naive_% (any model, either target) |
|---|---|
| 1d | -0.08% (LSTM, Open) |
| 5d | -1.85% (LSTM, Open) |
| 10d | -0.21% (LSTM, Open) |
| 20d | -5.49% (Linear Regression, Open) |
| 60d | +3.39% (Linear Regression, Open) |

This is a starker version of Phase 7's finding for High/Low (which stayed
positive at 1-day across all 5 model types, +5% to +19%, and only turned
negative at longer horizons). The reason is the target itself, not a
regression: "today's Close" is the textbook random-walk baseline for
tomorrow's Close, and Open's fair baseline (today's Close, per
`phase_9.md`'s own asymmetric-naive reasoning) is just as strong, since
overnight gaps are usually small. High/Low held constant was a comparatively
easier baseline to beat because a stock's daily High and Low genuinely
differ from its own Close, giving models real signal to add on top of "no
change." Predicting Open/Close instead removes exactly that easier target -
a legitimate, unflattering result, reported plainly per this project's own
established practice (see Phase 7's notes) rather than smoothed over.
Verified this wasn't a bug by reloading `phase9_lr_close_1d.pkl` and
`phase9_feature_scaler.pkl` directly and recomputing both MAEs by hand
(model 8.74, naive 8.41 - matches the logged -3.91% exactly).

## Result: directional accuracy is mostly a coin flip, except Open at 1 day

Most (Model, Target, Horizon) cells land in the 47-55% range for
`Directional_Accuracy_%`. The one consistent exception is the **Open**
target at the **1-day** horizon, where every model type clears 57%, up to
LSTM's 67.50% - noticeably better than Close's 1-day directional accuracy
(49.5-51.8%). This tracks with Open being more mechanically predictable than
Close: Open is close to "yesterday's Close plus a small, partly-continuing
overnight move," while Close absorbs a full day's trading on top of that.
The gap disappears by 5 days out, where both targets converge to ~50-54%.

## Result: range widens with horizon for every ticker/target/model - no exceptions, same as Phase 7

250/250 (25 tickers x 2 targets x 5 model types) comparisons between
horizon-1 and horizon-60 backtested `std_error` show the range widening, a
100% widen rate with zero exceptions - the same clean result Phase 7 found
for High/Low, now confirmed to carry over to Open/Close.

## Result: Open-to-Close spread accuracy - GRU is the most stable, LSTM degrades badly at 60d

Mean `MAE_Spread` (predicted Close-minus-Open vs actual Close-minus-Open) by
model type and horizon:

| Horizon | GRU | LSTM | Linear Regression | Random Forest | XGBoost |
|---|---|---|---|---|---|
| 1d | 10.85 | 9.47 | 9.85 | 10.04 | 10.25 |
| 5d | 11.52 | 11.10 | 10.27 | 13.33 | 12.38 |
| 10d | 12.30 | 15.70 | 10.59 | 12.38 | 14.49 |
| 20d | 11.73 | 20.07 | 10.77 | 13.81 | 16.95 |
| 60d | 10.95 | **56.94** | 11.15 | 15.34 | 16.38 |

Linear Regression and GRU stay roughly flat across all 5 horizons (~10-15),
while LSTM's spread error grows sharply with horizon and is a clear outlier
at 60d (56.94, 3-5x every other model type there) despite LSTM's own
individual Open/Close MAE at 60d (109-119) not being wildly out of line with
the other model types (93-106). This means LSTM's Open and Close predictions
are comparatively uncorrelated with each other at long horizons - their
individual errors don't cancel out when subtracted the way they do for the
other model types, whose Open/Close predictions apparently share more
correlated error at 60d. Worth watching if Phase 8's redesign surfaces
spread/move-size predictions directly, but not something this phase needed
to fix - the underlying per-target metrics are still reported and usable on
their own.

## Result: serving-model storage - 44 of 50 combos needed, 199MB set aside

`manage_model_storage.py` against `phase9_model_comparison_per_stock.csv`:
44/50 (horizon, target, model_type) combos are the serving choice for at
least one of the 25 stocks; 6 are never selected by any stock -
`(1d, Close, GRU)`, `(1d, Open, GRU)`, `(5d, Open, Random Forest)`,
`(10d, Close, Random Forest)`, `(20d, Close, GRU)`, `(20d, Close, Random
Forest)`. Those 6 moved to `models_evaluation_only/` (190MB - 3 of the 6 are
Random Forest, the largest file type). `models/` holds the other 44 (456MB).

## A known consequence: `app.py` and `train_models_phase7.py` don't run right now

Neither file is touched this phase, per `phase_9.md`'s own scope note
("Phase 8's dashboard redesign happens after Phase 9 is complete and
verified, not alongside it"). `app.py` imports `NEW_FEATURE_COLUMNS` and
`to_price` from `train_models_phase6.py`, which Step 6 deletes outright;
`train_models_phase7.py` imports six functions from the same deleted module.
Both will raise `ModuleNotFoundError` at import time until Phase 8 is
redone against Phase 9's Open/Close artifacts - an accepted, temporary
state, not an oversight. `train_models_phase7.py` itself is kept (not
deleted) as a historical record of how the 50 now-deleted `phase7_*_high/low*`
model files were produced, consistent with `phase_9.md` only listing
`train_models.py` and `train_models_phase6.py` for outright deletion.
